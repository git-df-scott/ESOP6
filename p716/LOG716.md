# (7,1,6) search log -- f^7 = a^7+b^7+c^7+d^7+e^7+g^7

Directory `p716/`.  Engine `engine716.c` implements the auditor's design in
`strata/SPEC_716.md`: a 4+3 meet in the middle with nested largest-part
windows, a blocked Bloom filter over all 3-sums d^7+e^7+g^7, exact 128-bit
verification of every Bloom positive.

Host: 4 cores (shared with another agent's runs in `strata/`), 15 GB RAM,
Linux 6.18, gcc -O3 -march=native -fopenmp.

## Engine notes (deviations and additions, all in the safe direction)
1. **Two filters.**  Besides the 3-sum Bloom the engine builds a small
   (TB^2/2 entries, 32 bits/entry) Bloom over 2-sums e^7+g^7, plus the mod
   49/29/43 *2-sum* residue mask (combined pass rate 0.0768).  The exact
   verifier uses these to skip the inner e-loop for hopeless d.  Both are
   one-sided (no false negatives) and every survivor is still settled by exact
   128-bit arithmetic, so completeness is untouched.  Without this a Bloom
   positive costs ~10^4 operations and the verifier, not the table, dominates.
2. **Verifier caps d at c** (SPEC's requirement), so each unordered solution is
   enumerated exactly once.
3. `verified` in the BAND line counts exact *pair* enumerations entered inside
   the verifier (the deep stage); `positives` counts 3-sum Bloom positives,
   every one of which is passed to the exact verifier.

## Measured constants
Mask pass rates, computed by brute force at start-up, match the SPEC exactly:
mod 49 3-sum 0.7551, mod 29 0.8621, mod 43 0.8605, product 0.5601
(2-sum: 0.3878 / 0.4483 / 0.4419, product 0.0768).

**However**, the observed mask pass rate on real leaves is 0.868, not 0.560:
R3 = f^7-a^7-b^7-c^7 is a signed 4-fold combination of seventh powers, whose
residues are strongly concentrated inside the 3-sum residue sets.  The masks
are therefore much less selective in situ than on random values; bloom queries
are 0.87 x leaves, not 0.56 x leaves.  (Verified at F=200, 300 and 600.)

### The idea, restated
Pass `r` of `Q` builds the 3-sum Bloom over only those `d^7+e^7+g^7 == r (mod
Q)`, and restricts the innermost enumerated base `c` to exactly the residue
classes with `c^7 == R2 - r (mod Q)`, so that `R3 = f^7-a^7-b^7-c^7 == r`.
Every leaf therefore belongs to exactly one pass and, in that pass, the
generating triple is in the table.  The c-loop shrinks by ~Q, so the **total**
leaf count over all Q passes equals a single-pass run; only the cheap (f,a,b)
loops and the table build repeat (the Q builds together cost one full build,
because `g` is likewise restricted).  This is strictly better than the hash
bucketing (`--nb`), which re-walks every leaf in every pass.

`Q=7` is the natural modulus: `x^7 == x (mod 7)` by Fermat, so the map
`c -> c^7 mod 7` is a bijection, every residue class of `c` is used in exactly
one pass, and the table splits into 7 classes of equal size.  (The same holds
mod 2, 3, 6, 14, 21 and 42, since `p-1 | 6` for `p = 2,3,7`; 42 is the largest
such modulus.  `Q=16` is *not* uniform: `x^7 == 0 (mod 16)` for all even x and
`x^7 == x^-1` for odd x, so `PRECNT[0] = 8` and the largest 3-sum residue
class holds 0.1717 of the table.)

### TASK 2 -- the bucketing gate
* **T6** (2,600], Q=16 vs Q=1, 16 passes summed:
  `leaves 73637464, masked 63938375, bloom_queries 63938375, solutions 0` --
  identical.  `positives` were 4704 (Q=16) vs 46589 (Q=1) and `verified` 0 vs
  3.  Those two are **not** equal, and cannot be: they depend on the Bloom's
  geometry, and the Q=16 per-pass filter is a different random object (sized
  for the largest residue class, holding ~1/16 of the entries, hence far
  underloaded and with a lower false-positive rate).  Rather than accept a
  weakened gate, a new test was added.
* **T7 (new) -- exact pass-sum identity on all five counters.**  A `--nobloom`
  switch was added to the engine: it bypasses the 3-sum Bloom entirely, so
  every masked leaf is handed to the exact verifier.  All five counters then
  become exact functions of the leaf set alone (the 2-sum filter is
  pass-independent -- `build_pairs` ignores the pass -- so `verified` stays
  deterministic too).  On (2,600]:

      Q=1 : 73637464 63938375 63938375 63938375 7832 0
      Q=2 : identical
      Q=7 : identical
      Q=16: identical
      Q=42: identical

  (fields: leaves masked bloom_queries positives verified solutions).  This is
  the unweakened gate: the Q passes partition the leaf set exactly, and the
  exact verifier is entered on exactly the same set of (R3, c) in every
  bucketing.  Together with T1 (every plant found under Q=16) the bucketing is
  validated.

### Deviation log (additions this session)
4. `--nobloom` (test-only): disables the 3-sum filter so that positives and
   verified become deterministic; used by T7.  Never used in production.
5. `run716.sh` (production driver): advances coverage one **chunk** of f at a
   time, each chunk a separate engine invocation over `(lo,hi]` running all Q
   residue passes internally.  A chunk is appended to `runs/coverage.txt` only
   after the invocation exits 0, i.e. after **all** Q passes have covered it.
   This is the restart checkpoint (the container has been killed twice today);
   re-running the driver resumes from the last recorded chunk.  Note that with
   Q > 1 the per-100-f BAND lines inside one invocation are *not* completed
   coverage -- only the chunk lines in `coverage.txt` are.  The table bound TB
   is the chunk's upper end, so early chunks build a much smaller table.

launched under `setsid nohup`, output in `runs/driver.log` + `runs/prod.log`,

`covlog.py` after every chunk.

`Q=7`: per-pass Bloom is `TB^3/6/7` entries at 16 bits/entry -- 1.33 GB at
TB=3000 and 6.1 GB at TB=5000, both inside the 8 GB budget (a single-pass table
at TB=5000 would be 41.7 GB).

**To resume after a container restart**: just re-run `./drive_all.sh`.
`run716.sh` reads `runs/coverage.txt`, sets FMIN to the highest `hi` already
recorded, and continues; at most the chunk in flight is lost and repeated.

Caveat on granularity: with `Q > 1` the per-100-f `BAND` lines *inside* one
invocation are cumulative over passes and are **not** completed coverage --
only the `COVERED` lines in `runs/coverage.txt` are.  Checkpoint spacing is the
chunk width: ~4-16 min on (1500,3000] at width 250, and ~50-155 min on
(3000,5000] at width 500.  Width is a trade against the table rebuild, which
costs ~TB^3/6 inserts per chunk however many passes it is split into (~74/W as
a fraction of the chunk's leaf work): 250 costs ~30%, 500 ~15%.
